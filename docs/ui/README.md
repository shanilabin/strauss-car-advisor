## ⚠️ חשוב: מה לקחת מאב-הטיפוס ומה לא

**מאב-הטיפוס לוקחים את השפה החזותית בלבד:** צבעים, טיפוגרפיה, כרטיס התוצאה, הקומפוזיציה. **את הזרימה לא לוקחים.** אב-הטיפוס מדגים מסכים, לא תהליך, ולכן הוא מבלבל.

### 🚫 1. העובד לא רואה את מסך הנציג, בשום שלב
**עובד ונציג הם שני אנשים שונים**, עם שני מסכים נפרדים:
- **העובד** משתמש ב-`/` וב-`/c/[id]`. **אין לו שום כפתור, קישור או לשונית שמובילים ל-`/rep`.**
- **הנציג** נכנס ל-`/rep` בכתובת ישירה, עם התחברות משלו (`rep@demo.local`).
- **בסרגל העליון של העובד אין כפתור "נציג".** באב-הטיפוס הכפתור קיים רק כדי לדפדף בין מסכי ההדגמה.
- **העובד גם לא צריך לראות את הנציג:** הוא רק רואה ש"שאלתי את נציג התחבורה", ואחר כך את התשובה כשהיא מגיעה. הוא לא רואה את מסך הנציג, את התור שלו או את שמו.
- **בדמו מול השופטות** פותחים שני חלונות דפדפן זה לצד זה: חלון עובד וחלון נציג.

### 🚫 2. אין כפתורי "הדגמה" בתוך המסך
באב-הטיפוס יש כפתורים כמו "הדגמת המתנה לנציג" ו"שליחת תשובה לדוגמה". **במוצר אין כפתורים כאלה.** המתנה לנציג מתחילה כשהשרת פותח שאלה, ותשובה מגיעה כשהנציג עונה במסך שלו.

### 🚫 3. אין דילוג לאפשרויות לפני שיש מספיק נתונים
באב-הטיפוס אפשר ללחוץ "הצגת אפשרויות" כשבפרופיל עדיין כתוב "חסר". **במוצר האפשרויות מופיעות רק כשהשרת מחזיר אותן**, כלומר רק אחרי שכל הנתונים הנחוצים נאספו. זה העיקרון המרכזי של המוצר: לא מחשבים בלי נתונים.

### 🚫 4. הרכב הנוכחי הוא לא חלופה
הרכב של היום מוצג ככרטיס "נטו היום" בכרטיס התוצאה, **לא** כפריט ברשימת הרכבים עם הפרש 0.

### ✅ 5. מה כן להוסיף: לאן אני בתהליך?
באב-הטיפוס לא ברור באיזה שלב העובד נמצא ומה הצעד הבא. **מוסיפים מחוון שלבים קטן בסרגל העליון:**
**① הפרטים שלך ← ② האפשרויות ← ③ ההשוואה**
השלב נגזר מסטטוס השיחה שמגיע מהשרת (`COLLECTING` ← ①, `READY` ← ②, `PRESENTED` ו-`WAITING_REP` ← ③). בכל מסך יש **פעולה ראשית אחת ברורה**.

## 2. איך המפרט מתמפה ל-API (נבדק מול החוזה)

| דרישת עיצוב | איפה זה ב-API | סטטוס |
|---|---|---|
| הפרש נטו, נטו היום, נטו בחלופה | `OptionResult.delta`, `.net_today`, `.net_option` (שקלים שלמים) | ✅ קיים |
| הסבר 2 שורות | `OptionResult.explanation` | ✅ |
| גרף מפל | `OptionResult.waterfall[]` (`key`, `label`, `delta`, `net_after`). סכום הצעדים = `delta` | ✅ |
| פירוט מלא (מס, ב"ל, בריאות, פנסיה, השתלמות...) | `OptionResult.breakdown` + `Comparison.today` | ✅ |
| עלות לחברה מול תקציב | `cost_to_company`, `group_budget` | ✅ |
| השתתפות + סטטוס אישור | `participation`, `participation_status` (`CONFIRMED` / `DEFAULT_PENDING` / `UNKNOWN`) | ✅ |
| "למה?" | `OptionResult.sources[]` (`field`, `label`, `ref`) | ✅ |
| שורת שקיפות | `Comparison.context` (שנות מס, גרסת כללים, hash) | ✅ |
| לא זכאי: סיבה בלי מספר | `eligibility.eligible=false`, `.reason`; כל המספרים `null` | ✅ |
| תוצאה חלקית / ממתין | `complete`, `missing[]`, `participation_status`, `ConversationState.status = WAITING_REP` | ✅ |
| "הכי משתלם" | `Comparison.best_option_id` | ✅ |
| כרטיסים בצ'אט | `MessageOut.cards[]`: `comparison` · `options` · `missing` · `rep_pending` | ✅ |
| תשובות מהירות | `AgentReply.quick_replies` | ✅ |
| מספר ילדים (מסלול משפחתי) | `Profile.children_under_23`. **שם השדה היסטורי**: גיל הסף בתווית/בשאלה נלקח מ-`/v1/config` (`specialTracks[].requires.childMaxAge`), לא נכתב בקוד | ✅ |
| **"הצג פעולות AI" בתוך הודעה** | **`MessageOut.trace[]`** (`kind`, `name`, `data`, `at`) בכל הודעת בוט, גם אחרי רענון | ✅ **נוסף עכשיו** בעקבות המפרט |
| תשובת נציג + תאריך תוקף | `POST /v1/rep/questions/{id}/answer` עם `value`, `effective_from` | ✅ |
| מסך נציג בלי שכר | `RepQuestionOut.context` מכיל רק עיסוק, קבוצה, רכב נוכחי ומבוקש | ✅ |
| שליחה כפולה | השרת מחזיר `409 already_answered` | ✅ |
| עדכון בזמן אמת | Supabase Realtime על `messages`, `conversations`, `rep_questions` | ✅ |

**מסקנה:** כל מה שהמפרט מבקש קיים ב-API, ואין צורך להמציא שום דבר בצד הלקוח.

## 3. החלטות שהמפרט השאיר פתוחות, וההמלצה הטכנית

### 3.1 אימות קבוצת הזכאות (המפרט, סעיף 9)
**המצב בפועל:** הקבוצה **נגזרת מהעיסוק** לפי טבלת העיסוקים בקונפיג (`occupations.json`). העובד מוסר עיסוק, והשרת קובע את הקבוצה. אם העובד טוען לקבוצה אחרת, נפתחת שאלה לנציג (`OCCUPATION_GROUP_MISMATCH`).
**המלצה לממשק:** כיתוב **"קבוצה ג׳ · לפי העיסוק שמסרת"**. בלי "מאומת", בלי מנעול. בדמו העובדים פיקטיביים. בפיילוט העיסוק יגיע ממערכת משאבי האנוש (SSO), ואז אפשר יהיה לכתוב "מאומת". זה סוגר את הסעיף הפתוח בלי לשנות שום דבר אחר במפרט.

### 3.2 צבע כרטיס התוצאה
המפרט קובע ש-Lime הוא **"הדגשות נקודתיות בלבד"**, אבל באב-הטיפוס כרטיס התוצאה כולו Lime. **צריך להכריע אחד מהשניים.** הניגודיות של Navy על Lime מצוינת, כך שאין בעיית נגישות. זו החלטה עיצובית בלבד.

### 3.3 סרגל לשוניות בנייד
באב-הטיפוס יש סרגל תחתון (רכבים / השוואה / צ'אט). המפרט (סעיף 4) מתאר "פעולה קבועה לצ'אט". סרגל ניווט כזה **לא** סותר את ה-API, כי הוא ניווט ולא פעולה עסקית, אבל כדאי שהמפרט יאשר אותו במפורש.

## 4. מה **לא** להעתיק מאב-הטיפוס
אב-הטיפוס הוא הדגמה חזותית מצוינת, אבל יש בו דברים של "הדמיה" שאסור שייכנסו למוצר:
1. **כפתורי הדגמה בתוך המסך** ("הדגמת המתנה לנציג", "שליחת תשובה לדוגמה"). במוצר, המתנה ותשובה מגיעות מהשרת.
2. **כפתור "נציג" בסרגל העליון של העובד.** העובד ונציג הם שני משתמשים שונים. ל-`/rep` נכנסים בכתובת ישירה עם התחברות.
3. **"הצגת אפשרויות" בזמן שבפרופיל עדיין מסומן "חסר".** המוצר לא מציג אפשרויות לפני שיש מספיק נתונים. השרת מחזיר `missing`.
4. **הרכב הנוכחי כפריט ברשימת החלופות** (Corolla Cross עם הפרש 0). ב-API "היום" הוא **הבסיס** (`Comparison.today`), לא חלופה. מציגים אותו בכרטיס התוצאה ("נטו היום"), לא ברשימה.
5. **גרף מפל סכמטי.** במוצר הגבהים מחושבים מ-`waterfall` בלבד.
6. **נתוני פרופיל של נועה:** באב-הטיפוס כתוב 2.25 נקודות זיכוי. הנכון הוא **2.75**.
7. **תסריט חיצוני שהוזרק לקובץ** (סינון אינטרנט, NetFree) **הוסר** מהעותק בריפו.
